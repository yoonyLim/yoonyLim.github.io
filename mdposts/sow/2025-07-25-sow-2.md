# [SOW 개발일지 2] 웨이브 데이터와 적 진입 경로 설계하기

## 1. 개요

### 1.1 사전 배경

SOW의 적은 맵 위에 무작정 스폰되는 대상이 아니라, 웨이브 데이터와 스테이지 경로를 따라 들어오는 존재다. 따라서 적 AI를 제대로 만들려면 개별 적의 행동만으로는 부족했다. 어떤 웨이브에서 어떤 적이 몇 마리 나오고, 어느 시점에 나오며, 어느 경로를 따라 Core Rune까지 이동할지를 표현할 데이터 구조가 필요했다.

이 시기의 작업은 적 AI를 웨이브 시스템에 연결하기 위한 중간 계층을 만드는 것에 가까웠다. C++에서는 웨이브 구조체와 진입 경로 Actor, 경로를 따라가는 Component와 Behavior Tree Task를 만들고, 실제 스테이지 구성은 Blueprint, DataTable, 맵 배치와 함께 연결되도록 했다.

### 1.2 수행 요약

처음에는 테스트용 웨이브 구조를 만들고, 이후 단일 경로에서 동적 경로, 복수 경로로 확장했다. 웨이브 적이 스폰되면 자신에게 가장 가까운 진입 경로를 찾고, 해당 경로의 Spline Point를 따라 이동하게 했다.

이 구조의 핵심은 적이 "목표 지점 하나"만 알고 움직이는 것이 아니라, 웨이브와 맵이 제공하는 경로를 따라 단계적으로 이동한다는 점이다.

## 3. 웨이브를 표현하는 데이터 구조

웨이브 구조는 `FMonsterSpawnData`와 `FWaveInfo`로 나누었다. 하나의 웨이브 안에는 여러 종류의 몬스터 스폰 데이터가 들어가고, 각 몬스터 데이터는 타입, 수량, 스폰 시간, 스폰 포인트 인덱스를 가진다.

```cpp
USTRUCT(BlueprintType)
struct SOW_API FMonsterSpawnData : public FTableRowBase
{
    GENERATED_BODY()

    UPROPERTY(EditAnywhere, BlueprintReadWrite)
    TSubclassOf<ASOWCharacterEnemyBase> MonsterType;

    UPROPERTY(EditAnywhere, BlueprintReadWrite)
    int32 MonsterCount;

    UPROPERTY(EditAnywhere, BlueprintReadWrite)
    float SpawnTime;

    UPROPERTY(EditAnywhere, BlueprintReadWrite)
    TArray<int32> SpawnPointIndices;
};
```

`FWaveInfo`는 웨이브 단위의 정보를 담는다.

```cpp
USTRUCT(BlueprintType)
struct SOW_API FWaveInfo : public FTableRowBase
{
    GENERATED_BODY()

    UPROPERTY(EditAnywhere, BlueprintReadWrite)
    int32 WaveNum;

    UPROPERTY(EditAnywhere, BlueprintReadWrite)
    TArray<FMonsterSpawnData> MonsterSpawnData;

    UPROPERTY(EditAnywhere, BlueprintReadWrite)
    float InterludeDuration;

    UPROPERTY(EditAnywhere, BlueprintReadWrite)
    float WaveDuration;
};
```

이 구조를 `FTableRowBase`로 만든 이유는 UE의 DataTable과 자연스럽게 연결하기 위해서였다. 웨이브 밸런스는 자주 바뀌는 데이터이므로 C++에 고정하면 반복 작업이 너무 느려진다. 반대로 모든 것을 Blueprint에만 두면 구조가 흩어져서 읽기 어려워진다. C++에서는 데이터의 형태를 고정하고, 실제 값은 DataTable과 Blueprint에서 조정하는 방식이 가장 적절했다.

## 4. Spline 기반 EnemyIncomingRoute

진입 경로는 `AEnemyIncomingRoute` Actor로 표현했다. 내부에는 `USplineComponent`를 두고, 맵 생성 또는 배치 흐름에서 전달된 위치 배열을 Spline Point로 변환한다.

```cpp
AEnemyIncomingRoute::AEnemyIncomingRoute()
{
    PrimaryActorTick.bCanEverTick = false;

    IncomingRoute = CreateDefaultSubobject<USplineComponent>("Incoming Route");
    SetRootComponent(IncomingRoute);
    IncomingRoute->SetMobility(EComponentMobility::Static);
}

void AEnemyIncomingRoute::SetSplinePointsFromLocations(const TArray<FVector>& Locations)
{
    IncomingRoute->ClearSplinePoints(true);

    for (const FVector& Location : Locations)
    {
        FVector NewLocation = FVector(Location.X, Location.Y, Location.Z + 10.f);
        IncomingRoute->AddSplinePoint(NewLocation, ESplineCoordinateSpace::World, true);
    }

    IncomingRoute->UpdateSpline();
}
```

Spline을 사용한 이유는 경로가 단순한 직선 배열이 아니기 때문이다. 맵 타일 구조가 바뀌면 경로도 달라지고, 경로를 시각화하거나 Spline Mesh로 표시해야 할 필요도 있었다. `SetSplinePointsFromLocations`에서는 기존 Spline Mesh를 지우고, 새 위치 배열을 받아 Spline과 표시 Mesh를 다시 구성한다.

이 작업은 개발 중 디버깅에도 도움이 되었다. 적이 이상한 방향으로 이동할 때 "AI가 잘못 판단했는지", "스폰 위치가 잘못되었는지", "경로 데이터가 틀렸는지"를 경로 표시만 보고 빠르게 좁힐 수 있었기 때문이다.

## 5. 적이 경로를 기억하는 Component

각 적은 `UEnemyIncomingRouteComponent`를 가진다. 이 Component는 적이 따라갈 Route와 현재 Spline Point Index를 들고 있고, Behavior Tree Task는 이 Component를 통해 다음 목표 지점을 가져온다.

```cpp
void UEnemyIncomingRouteComponent::SetIncomingRoute(AEnemyIncomingRoute* NewIncomingRoute)
{
    EnemyIncomingRoute = NewIncomingRoute;
}

bool UEnemyIncomingRouteComponent::HasReachedEnd() const
{
    if (IncomingRouteIndex > EnemyIncomingRoute->GetNumberOfPoints() - 1)
        return true;

    return false;
}

FVector UEnemyIncomingRouteComponent::GetCurrentIndexPosition() const
{
    return EnemyIncomingRoute->GetCurrentIncomingIndexPosition(IncomingRouteIndex);
}
```

이 Component를 별도로 둔 이유는 경로 이동 상태를 적 캐릭터 본체에서 분리하기 위해서였다. 적 캐릭터 클래스는 이미 체력, 애니메이션, 공격, GAS, UI, 사운드 등 많은 책임을 가진다. 경로 관련 인덱스와 Route 참조까지 캐릭터에 직접 넣으면 이후 기능이 빠르게 비대해진다.

Component로 분리하면 Behavior Tree Task는 "현재 인덱스 위치를 달라", "다음 인덱스로 넘어가라", "끝에 도착했나"만 요청하면 된다.

## 6. 가장 가까운 경로 선택

복수 경로가 생기면서 스폰된 적이 어떤 Route를 따라가야 하는지가 중요해졌다. 적은 맵의 TileSpawner가 가진 경로 목록을 가져오고, 자기 위치와 각 Route의 첫 번째 Spline Point 사이 거리를 비교해 가장 가까운 경로를 선택한다.

```cpp
AEnemyIncomingRoute* ASOWCharacterEnemyBase::FindClosestIncomingRoute() const
{
    TArray<AEnemyIncomingRoute*> AvailableRoutes = TileSpawner->GetSpawnedEnemyRoutes();

    AEnemyIncomingRoute* ClosestRoute = nullptr;
    float MinSquaredDistance = TNumericLimits<float>::Max();
    FVector EnemyLocation = GetActorLocation();

    for (AEnemyIncomingRoute* Route : AvailableRoutes)
    {
        if (Route && Route->GetNumberOfPoints() > 0)
        {
            FVector RouteStartLocation = Route->GetCurrentIncomingIndexPosition(0);
            float CurrentSquaredDistance = FVector::DistSquared(
                EnemyLocation,
                RouteStartLocation
            );

            if (CurrentSquaredDistance < MinSquaredDistance)
            {
                MinSquaredDistance = CurrentSquaredDistance;
                ClosestRoute = Route;
            }
        }
    }

    return ClosestRoute;
}
```

이 방식은 매우 복잡한 알고리즘은 아니지만, 웨이브 시스템에서는 충분히 안정적이었다. 스폰 포인트와 경로 시작점이 맵 구성 단계에서 맞춰져 있다면, 스폰된 적은 자기에게 가장 자연스러운 경로를 선택한다. 또한 `DistSquared`를 사용해 불필요한 제곱근 계산을 피했다.

## 7. Behavior Tree Task와 경로 진행

경로를 따라가는 Task는 현재 인덱스의 위치를 Blackboard에 저장하고 다음 인덱스로 넘긴다. 경로 끝에 도착하면 상태를 `Attacking`으로 전환한다.

```cpp
if (Enemy->GetEnemyIncomingRouteComponent()->HasReachedEnd())
{
    Enemy->GetAIController()->UpdateCurrentState(EEnemyStates::Attacking);
    FinishLatentTask(OwnerComp, EBTNodeResult::Succeeded);
    return EBTNodeResult::Succeeded;
}

FVector TargetLocation =
    Enemy->GetEnemyIncomingRouteComponent()->GetCurrentIndexPosition();

OwnerComp.GetBlackboardComponent()->SetValueAsVector("TargetLocation", TargetLocation);
Enemy->GetEnemyIncomingRouteComponent()->IncrementIncomingRouteIndex();
```

초기에는 AI MoveTo를 사용해 Spline Point를 하나씩 이동하는 구조를 실험했다. 이후 웨이브 적이 많아지고 경로가 많아지면서, 일부 적 타입은 직접 전방 방향으로 이동시키는 Task도 함께 사용하게 되었다. 중요한 것은 이동 방식이 달라져도 경로 상태를 관리하는 Component와 Blackboard Key는 유지된다는 점이었다.

## 8. 후기

이 단계에서 가장 크게 배운 점은 웨이브 시스템을 "스폰 타이머"로만 보면 안 된다는 것이었다. SOW에서 웨이브는 적 수량과 시간표뿐 아니라 맵 경로, 적 AI 상태, Core Rune 충돌, 보상 지급까지 이어지는 하나의 파이프라인이었다.

그래서 웨이브 구조체, Route Actor, Route Component, Behavior Tree Task를 따로 만들었다. 각 조각은 작지만, 이 조각들이 연결되면서 "적이 어디서 나오고 어디로 가는지"를 안정적으로 설명할 수 있게 되었다.
