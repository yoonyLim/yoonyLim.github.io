# [SOW 개발일지 3] Core Rune, 플레이어블 스테이지, 웨이브 GameMode

## 1. 개요

### 1.1 사전 배경

적 AI와 웨이브 경로가 준비되면 다음 문제는 게임 모드 전체의 승패 흐름이었다. SOW의 플레이 목표는 적을 모두 처치하는 것만이 아니라, 웨이브 동안 Core Rune을 지키는 것이다. 따라서 적이 경로 끝에 도착했을 때 Core Rune에 데미지를 주고, 적 사망은 보상과 웨이브 진행에 반영되어야 했다.

이 시기의 작업은 개별 시스템을 실제 플레이 가능한 스테이지 흐름으로 묶는 과정이었다. WaveGameMode에서 재화, 터렛 수, 스테이지 종료 이벤트를 관리하고, 적 캐릭터는 Core Rune과 충돌했을 때 GAS Effect를 통해 데미지를 적용하도록 연결했다.

### 1.2 수행 요약

기존에는 적, 터렛, Core Rune, 웨이브 데이터가 각각 존재했지만 게임 모드 관점에서 하나의 루프로 묶이지 않았다. `init: game mode`, `feat: new game mode`, `feat: core rune health interaction`, `feat: playable stage` 커밋을 거치면서 웨이브 시작, 재화 갱신, 터렛 제한, Core Rune 체력 변화, 스테이지 선택이 하나의 플레이 흐름으로 이어졌다.

## 3. WaveGameMode의 역할

SOW에서 GameMode는 웨이브 전체의 메타 상태를 들고 있다. 여기에는 일회성 재화, 현재 소환된 터렛 수, 스테이지 종료 이벤트가 포함된다.

```cpp
DECLARE_DYNAMIC_MULTICAST_DELEGATE_OneParam(
    FOnOneTimeCurrencyChanged,
    int32,
    TotalCurrency
);

DECLARE_DYNAMIC_MULTICAST_DELEGATE_OneParam(
    FOnTurretsNumChanged,
    int32,
    TotalTurrets
);

DECLARE_DYNAMIC_MULTICAST_DELEGATE(FOnStageEnd);
```

이 Delegate들은 Blueprint UI와도 연결하기 쉽다. C++에서 재화나 터렛 수를 바꾸면 UI는 Event Dispatcher를 통해 갱신된다. 이 구조를 잡아두면 웨이브와 전투 로직이 UI 위젯을 직접 참조하지 않아도 된다.

```cpp
class SOW_API AWaveGameMode : public AGameModeBase
{
    GENERATED_BODY()

private:
    int32 Currency = 0;
    int32 SummonedTurretsNum = 0;

public:
    UPROPERTY(BlueprintAssignable, BlueprintCallable, Category = "Event Dispatcher")
    FOnOneTimeCurrencyChanged OnOneTimeCurrencyChanged;

    UPROPERTY(BlueprintAssignable, BlueprintCallable, Category = "Event Dispatcher")
    FOnTurretsNumChanged OnTurretsNumChanged;

    UPROPERTY(BlueprintAssignable, BlueprintCallable, Category = "Event Dispatcher")
    FOnStageEnd OnStageEnd;

    UPROPERTY(EditAnywhere, BlueprintReadWrite, Category = "Turerts")
    int32 MaxturretsNum = 10;
};
```

이 GameMode는 "웨이브가 돌아가는 중에 어떤 전역 상태가 바뀌는가"를 한곳에 모으는 역할을 했다. 적 사망 보상, 터렛 판매 환불, 터렛 소환 제한, 스테이지 종료 UI가 서로 다른 시스템에 흩어지지 않도록 하는 것이 목적이었다.

## 4. 재화와 터렛 제한

운빨 가차 랜덤 디펜스에서 재화는 전투 속도를 조절하는 핵심 자원이다. 적을 처치해서 얻은 재화로 터렛을 더 소환하거나 강화할 수 있기 때문에, 적 사망과 GameMode의 재화 갱신이 연결되어야 했다.

```cpp
void AWaveGameMode::AddCurrency(int32 AddedCurrency)
{
    Currency += AddedCurrency;
    OnOneTimeCurrencyChanged.Broadcast(Currency);
}
```

이후 터렛 수 제한도 GameMode에서 관리했다. 제한을 넘으면 Blueprint Alert를 띄우고, 가능할 때만 소환 수를 증가시킨다.

```cpp
bool AWaveGameMode::CanSpawnTurret()
{
    if (SummonedTurretsNum >= MaxturretsNum)
    {
        AlertMaxTurrets();
        return false;
    }

    SummonedTurretsNum++;
    OnTurretsNumChanged.Broadcast(SummonedTurretsNum);

    return true;
}
```

터렛 수 제한은 단순한 UI 제약이 아니었다. SOW의 전투는 적 웨이브와 터렛 배치가 서로 맞물리는 구조이므로, 터렛을 무제한으로 둘 수 있으면 웨이브 밸런스가 의미를 잃는다. 반대로 제한을 GameMode에 두면 UI, 소환 시스템, 밸런스 데이터가 같은 기준을 바라볼 수 있다.

## 5. Core Rune에 도달한 적 처리

적이 경로 끝에 도착하면 이제 플레이어와 터렛을 공격하는 것이 아니라 Core Rune에 직접 피해를 주어야 한다. 이 흐름은 `ASOWCharacterEnemyBase::OnBeginOverlap`에서 처리했다.

```cpp
if (Cast<ASOWCharacterCoreRune>(OtherActor)
    && GetEnemyIncomingRouteComponent()->IsCloseToEnd(2))
{
    ShardDropAmount = 0;
    HealthBarWidget->SetHiddenInGame(true);

    FGameplayEffectContextHandle EffectContext =
        USOWBlueprintFunctionLibrary
            ::NativeGetSOWAbilitySystemComponentFromActorInfo(this)
            ->MakeEffectContext();

    EffectContext.AddSourceObject(this);
}
```

여기서 `IsCloseToEnd(2)` 조건을 둔 이유가 중요하다. Core Rune과 겹치기만 했다고 무조건 데미지를 주면 안 된다. 경로 중간에서 우연히 충돌하거나, 맵 배치상 가까운 위치를 지나가는 경우가 있을 수 있다. 따라서 경로 컴포넌트가 "거의 끝에 도착했다"고 판단할 때만 Core Rune 피해 처리를 허용했다.

이후 대상 타입을 다시 확인하고, Core Rune이면 GAS Effect를 적용한다.

```cpp
if (TargetType == ESOWCharacterType::CoreRune)
{
    USOWBlueprintFunctionLibrary::NativeGetSOWAbilitySystemComponentFromActorInfo(this)
        ->ApplyGameplayEffectSpecToTarget(
            *USOWBlueprintFunctionLibrary
                ::NativeGetSOWAbilitySystemComponentFromActorInfo(this)
                ->MakeOutgoingSpec(DamageEffect, 1.f, EffectContext).Data.Get(),
            USOWBlueprintFunctionLibrary
                ::NativeGetSOWAbilitySystemComponentFromActorInfo(OtherActor)
        );
}
```

이렇게 만든 이유는 Core Rune도 예외적인 오브젝트가 아니라 SOW의 전투 규칙을 따르는 대상으로 다루기 위해서였다. 플레이어, 터렛, Core Rune 모두 캐릭터 타입과 ASC를 통해 효과를 주고받을 수 있으면, 데미지 계산과 상태 처리의 기준이 일관된다.

## 6. 사망 이벤트 중복 문제

Core Rune 충돌이 들어오면서 적 사망 이벤트가 여러 경로에서 호출될 수 있는 문제가 생겼다. 체력이 0이 되었을 때도 사망 이벤트가 발생하고, Core Rune에 도달했을 때도 Wave 진행을 위해 사망처럼 처리해야 했기 때문이다.

이 문제는 포트폴리오에서 보여주기 좋은 지점이라고 생각한다. 기능이 늘어나면 "잘 되는 코드"보다 "두 번 실행되면 안 되는 코드"가 더 중요해진다. 적 사망 이벤트는 보상, 웨이브 카운트, 이펙트, UI 갱신을 모두 건드리므로 중복 호출되면 재화가 두 번 들어오거나 웨이브가 빨리 끝날 수 있었다.

그래서 사망 처리에는 `bIsDead` 같은 상태 가드를 두고, Core Rune 충돌에서는 Shard 보상을 0으로 바꾸어 일반 처치와 구분했다.

```cpp
if (NewHealth <= 0 && !bIsDead)
{
    BroadcastEnemyDeath();
    HealthBarWidget->SetHiddenInGame(true);
    bIsDead = true;
}
```

이후 `fix: duplicate enemy death event`, `fix: double enemy death event` 커밋에서 이 흐름을 계속 다듬었다. 게임플레이 이벤트는 한 번만 발생해야 하는지, 여러 번 누적되어야 하는지 경계가 분명해야 한다는 것을 배운 작업이었다.

## 7. 플레이어블 스테이지로 묶기

`feat: playable stage` 시점에는 개별 기능을 실제 스테이지로 묶었다. 웨이브 데이터가 있고, 적이 Route를 따라 오고, Core Rune이 피해를 받고, 터렛 소환 수와 재화가 GameMode에서 관리되는 흐름이 하나의 플레이 가능한 단계로 합쳐졌다.

이때부터는 디버깅 방식도 달라졌다. 이전에는 적 하나를 스폰해 공격이 되는지 확인했다면, 이제는 "웨이브 하나를 시작했을 때 적이 몇 마리 살아남는가", "Core Rune에 몇 마리가 도달하는가", "보상이 의도대로 들어오는가", "터렛 제한이 전투 난이도를 망가뜨리지 않는가"를 같이 확인해야 했다.

## 8. 후기

이 단계는 SOW가 단순 기능 모음에서 게임 루프로 바뀌는 시기였다. 적 AI, 웨이브 데이터, Core Rune, 터렛 수 제한, 재화가 연결되면서 실제 플레이 테스트가 가능해졌다.

개인적으로는 Core Rune 충돌 처리와 사망 이벤트 중복 수정이 기억에 남는다. 겉으로 보기에는 작은 조건문과 플래그처럼 보이지만, 그 조건이 운빨 가차 랜덤 디펜스의 승패와 보상 계산을 지키는 역할을 했다. 시스템을 만들 때는 "언제 실행되는가"만큼 "언제 실행되면 안 되는가"도 함께 설계해야 한다는 것을 확인한 작업이었다.
