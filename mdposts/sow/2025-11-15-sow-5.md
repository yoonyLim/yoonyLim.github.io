# [SOW 개발일지 5] 보스, 샤드 보상, 튜토리얼, 빌드 전 밸런싱

## 1. 개요

### 1.1 사전 배경

후반 작업은 시스템을 새로 만드는 것보다, 이미 만들어진 시스템을 실제 플레이 가능한 콘텐츠로 채우고 다듬는 일이 많았다. 웨이브 데이터가 늘어나고, 스테이지가 네 개로 확장되고, 보스가 추가되면서 적 AI와 웨이브 시스템은 더 많은 조합을 견뎌야 했다.

이 시기에는 적 사망 보상, 샤드 드롭, 사망 이펙트, 보스 추가, 튜토리얼, 스테이지 썸네일, 최종 밸런스 조정이 이어졌다. C++ 코드와 `.uasset` 기반 작업이 함께 섞였기 때문에, 포트폴리오 관점에서는 "어떤 시스템을 만들었는가"뿐 아니라 "그 시스템을 실제 콘텐츠에 어떻게 적용했는가"를 보여주는 것이 중요하다.

### 1.2 수행 요약

적 사망 이벤트를 통해 샤드 보상을 지급하고, Core Rune에 도달한 적은 보상을 주지 않도록 구분했다. 이후 보스와 여러 스테이지, 튜토리얼 맵, Endless 맵 초기화, 웨이브 데이터 재밸런싱을 거치면서 프로젝트를 빌드 전 상태까지 다듬었다.

## 3. 적 사망과 보상 이벤트

SOW에서 적 사망은 단순히 Actor를 제거하는 이벤트가 아니다. 웨이브 카운트, 보상, UI, 사운드, 이펙트가 모두 이 시점에 연결된다. 적이 사망하면 `BroadcastEnemyDeath`를 통해 드롭량과 적 클래스를 전달한다.

```cpp
void ASOWCharacterEnemyBase::BroadcastEnemyDeath()
{
    OnEnemyDeath.Broadcast(ShardDropAmount, GetClass());

    if (EnemyDeathSound)
    {
        UGameplayStatics::PlaySoundAtLocation(
            this,
            EnemyDeathSound,
            GetActorLocation()
        );
    }
}
```

이 Delegate는 적 처치 보상과 웨이브 진행을 느슨하게 연결하는 지점이다. 적 캐릭터가 직접 GameMode나 재화 Manager의 상세 구현을 모두 알 필요 없이, "내가 죽었다"는 사실과 보상 정보를 방송하면 된다.

반대로 Core Rune에 도착한 적은 처치된 것이 아니므로 보상을 주면 안 된다. 그래서 Core Rune 충돌 처리에서는 `ShardDropAmount = 0`으로 바꾸고 사망 이벤트를 발생시켰다.

```cpp
if (Cast<ASOWCharacterCoreRune>(OtherActor)
    && GetEnemyIncomingRouteComponent()->IsCloseToEnd(2))
{
    ShardDropAmount = 0;
    HealthBarWidget->SetHiddenInGame(true);

    GetSOWAbilitySystemComponent()->AddLooseGameplayTag(
        SOWGameplayTags::Shared_Ability_Death
    );

    GetSOWAbilitySystemComponent()->AddLooseGameplayTag(
        SOWGameplayTags::Shared_Status_Dead
    );

    BroadcastEnemyDeath();
}
```

이 구분은 운빨 가차 랜덤 디펜스에서 중요했다. 플레이어가 적을 막지 못해 Core Rune이 피해를 입은 상황인데도 보상을 받으면, 실패가 오히려 자원 이득으로 연결될 수 있기 때문이다.

## 4. 샤드 드롭과 사망 이펙트

`feat: enemy death effects (shard drops, dissolve effect)`와 `feat: enemies drop shards`에서는 사망 이벤트의 결과를 시각적으로 드러내는 작업이 들어갔다. 적이 죽으면 샤드가 떨어지고, dissolve 이펙트나 사운드가 함께 재생되어 처치 피드백을 강화했다.

여기서 C++의 역할은 이벤트의 기준점을 제공하는 것이었다. 실제 드롭 Actor, Niagara, Material, Blueprint 연출은 에디터 자산과 함께 구성되지만, 그 모든 연출은 결국 적 사망 이벤트가 한 번만 정확히 발생한다는 전제 위에 올라간다.

후반에 적 수가 많아지면서 이 부분은 더 중요해졌다. 한 웨이브에서 수십 마리의 적이 죽는 상황에서는 중복 이벤트 하나가 재화 경제를 크게 흔들 수 있고, 반대로 이벤트 누락은 플레이어가 처치 보상을 받지 못하는 문제로 이어진다.

## 5. 보스와 스테이지 확장

`feat: four stages`와 `feat: addition boss`를 거치면서 SOW는 여러 스테이지와 보스 콘텐츠를 갖추게 되었다. 이때 기존 적 시스템을 보스에도 사용할 수 있어야 했다.

보스를 일반 적과 완전히 별도 시스템으로 만들면 빠르게 구현할 수는 있지만, 웨이브, 사망 이벤트, GAS Attribute, Behavior Tree, UI 체력 표시를 다시 만들어야 한다. 그래서 보스도 가능한 한 기존 적 베이스와 DataTable, Ability 흐름 위에 올리는 방향이 유지되었다.

`EEnemyTypes`에도 일반 적과 보스가 함께 정의되어 있다.

```cpp
UENUM(BlueprintType)
enum class EEnemyTypes : uint8
{
    DesertBat UMETA(DisplayName = "DesertBat"),
    DesertMage UMETA(DisplayName = "DesertMage"),
    PunchCactus UMETA(DisplayName = "PunchCactus"),

    // Bosses
    DesertBoss UMETA(DisplayName = "DesertBoss"),
    ForestBoss UMETA(DisplayName = "ForestBoss"),
    HorrorBoss UMETA(DisplayName = "HorrorBoss"),
    IcelandBoss UMETA(DisplayName = "IcelandBoss"),
    ToylandBoss UMETA(DisplayName = "ToylandBoss"),
};
```

이렇게 타입을 확장해두면 보스도 DataTable Row를 통해 체력, 공격력, 애니메이션, 보상 등을 조정할 수 있다. 웨이브 데이터 입장에서는 보스도 `MonsterType`으로 스폰되는 적의 한 종류가 된다.

## 6. 튜토리얼과 플레이 흐름

후반에는 시스템을 설명하는 튜토리얼도 필요했다. 운빨 가차 랜덤 디펜스는 플레이어가 알아야 할 정보가 많다. 터렛을 어디에 놓는지, 웨이브는 어떻게 시작되는지, 적은 어디서 오는지, Core Rune을 왜 지켜야 하는지, 샤드는 어떤 의미인지 자연스럽게 안내해야 한다.

`feat: tutoiral init`, `feat: tutorial halfway or a third..?`, `feat: tutorial`, `fix: tutorial adjustments` 커밋은 이 안내 흐름을 만든 작업이었다. 코드 관점에서 새로운 알고리즘을 만든 작업은 아닐 수 있지만, 포트폴리오에서는 중요하다. 시스템을 만들었더라도 플레이어가 이해하지 못하면 실제 게임으로 작동하지 않기 때문이다.

튜토리얼 작업은 기존 GameMode, UI, 웨이브 시작 로직이 충분히 분리되어 있어야 가능했다. 이미 만들어둔 이벤트와 Blueprint Callable 함수들이 있었기 때문에, 튜토리얼은 시스템을 복사하지 않고 기존 흐름을 단계적으로 노출하는 방향으로 구성할 수 있었다.

## 7. 최종 밸런싱

마지막 `update: re-balance` 커밋은 프로젝트 후반 작업의 성격을 잘 보여준다. 적 AI와 웨이브 시스템은 완성 여부보다 체감 난이도가 더 중요하다. 코드가 정상이어도 적 체력이 너무 높으면 지루하고, 너무 낮으면 웨이브가 무의미해진다. 적 이동 속도, 스폰 수, 스폰 시간, 터렛 제한, 보상량, 보스 체력은 함께 조정되어야 한다.

이때 앞서 만든 구조들이 도움이 되었다.

1. 웨이브 구조체가 있으므로 스폰 수와 시간을 DataTable에서 조정할 수 있다.
2. 적 능력치가 DataTable과 GAS 초기화로 연결되어 있어 타입별 수치를 바꿀 수 있다.
3. 사망 이벤트가 보상을 방송하므로 적별 샤드량을 조절할 수 있다.
4. 터렛 제한이 GameMode에 있어 방어력 상한을 조정할 수 있다.

즉, 후반 밸런싱은 새로운 코드를 많이 쓰는 작업이 아니라, 초반에 만든 데이터 중심 구조가 실제로 효과를 내는지 확인하는 단계였다.

## 8. 후기

SOW 후반 작업은 "시스템을 만들었다"에서 끝나지 않고 "그 시스템으로 게임을 완성 가능한 상태까지 끌고 갔다"는 점에서 의미가 있었다. 적 AI, GAS 데미지, 웨이브 데이터, GameMode, Core Rune, 보상 이벤트가 연결되어 있었기 때문에 보스, 튜토리얼, Endless 맵, 최종 밸런싱까지 확장할 수 있었다.

개인 포트폴리오로 정리한다면 이 프로젝트에서 보여주고 싶은 점은 두 가지다. 첫째, UE5의 Behavior Tree와 GAS를 실제 게임 루프에 연결한 경험이다. 둘째, 운빨 가차 랜덤 디펜스에서 적 AI는 캐릭터 하나의 코드가 아니라 데이터, 경로, 보상, 승패 조건까지 이어지는 시스템이라는 것을 이해하고 구현했다는 점이다.
