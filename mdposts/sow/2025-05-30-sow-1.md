# [SOW 개발일지 1] 적 AI와 GAS 기반 전투 연결하기

## 1. 개요

### 1.1 사전 배경

SOW는 Unreal Engine 5로 만든 운빨 가차 랜덤 디펜스 프로젝트다. 플레이어가 스테이지를 선택하고, 랜덤 가차로 얻은 터렛과 스킬을 활용해 몰려오는 적을 막는 구조이기 때문에 적 AI는 단순한 보조 기능이 아니라 게임의 흐름을 만드는 핵심 시스템이었다.

이번 개발일지 시리즈는 전체 팀 작업을 모두 나열하기보다, 내 GitHub 계정으로 작성된 커밋만 골라 SOW에서 맡았던 개발 과정을 정리한다. 기준으로 사용한 author 정보는 아래와 같다.

```text
Hayoon Lim / 임하윤 <64838255+yoonyLim@users.noreply.github.com>
```

SOW의 Gameplay Ability System, UI, 타일 생성, 터렛 전투는 팀 전체가 함께 사용하는 공통 시스템이었다. 그중 내가 집중한 부분은 적 캐릭터가 그 공통 시스템 위에서 실제 게임플레이 객체로 동작하도록 연결하는 일이었다. 적이 Behavior Tree로 상태를 바꾸고, DataTable에서 능력치를 읽고, 공격 애니메이션 타이밍에 GAS GameplayEffect를 적용하는 흐름을 만드는 것이 첫 번째 목표였다.

### 1.2 수행 요약

초기에는 적 개발용 브랜치와 레벨을 분리하고, 적 캐릭터와 AI Controller가 Behavior Tree를 실행할 수 있는 기반을 만들었다. 이후 근접 공격 애니메이션과 Animation Notify State를 통해 공격 판정을 만들고, 맞은 대상에게 GAS Effect를 적용하는 방식으로 전투 시스템과 연결했다.

이 단계에서 중요했던 점은 "적이 공격한다"라는 동작을 캐릭터 클래스 안에 전부 넣지 않는 것이었다. 적의 의사결정은 Behavior Tree와 Blackboard가 맡고, 실제 공격 타이밍은 애니메이션 Notify가 맡고, 수치 적용은 GAS가 맡도록 나누었다.

## 3. Behavior Tree를 실행하는 AI Controller

적 AI의 첫 번째 기준점은 `AEnemyBaseAIController`였다. 적이 스폰되어 Controller에 Possess되면, 적 캐릭터가 들고 있는 Behavior Tree를 읽고 Blackboard를 초기화한 뒤 실행한다.

```cpp
void AEnemyBaseAIController::OnPossess(APawn* PossessedPawn)
{
    Super::OnPossess(PossessedPawn);

    if (ASOWCharacterEnemyBase* const Enemy = Cast<ASOWCharacterEnemyBase>(PossessedPawn))
    {
        if (UBehaviorTree* const BehaviorTree = Enemy->GetBehaviorTree())
        {
            UBlackboardComponent* Bboard;
            UseBlackboard(BehaviorTree->BlackboardAsset, Bboard);
            Blackboard = Bboard;

            Enemy->SetAIController(this);

            if (AActor* CoreRune = UGameplayStatics::GetActorOfClass(
                GetWorld(), ASOWCharacterCoreRune::StaticClass()))
            {
                GetBlackboardComponent()->SetValueAsObject("AttackTarget", CoreRune);
            }

            UpdateCurrentState(EEnemyStates::FollowingIncomingRoute);
            RunBehaviorTree(BehaviorTree);
        }
    }
}
```

여기서 중요한 흐름은 세 가지다.

1. 적 캐릭터가 Behavior Tree를 소유하고, AI Controller는 그것을 실행한다.
2. Blackboard의 기본 공격 대상은 Core Rune으로 설정한다.
3. 시작 상태를 `FollowingIncomingRoute`로 두어 웨이브 적이 스폰 직후 경로를 따라 이동하게 만든다.

초기에는 AI Perception으로 플레이어, 터렛, Core Rune을 감지하는 방식도 함께 실험했다. 하지만 SOW의 주된 게임 루프는 "적이 정해진 웨이브 경로를 따라 Core Rune으로 들어온다"에 가까웠기 때문에, 기본 목표는 Core Rune으로 고정하고 이후 도발이나 우선순위에 따라 Target을 바꾸는 방향이 더 안정적이었다.

## 4. DataTable에서 Blackboard로 이어지는 초기화

적마다 공격 속도, 공격 반경, 목표 우선순위가 다르기 때문에 이 값들은 코드에 박아두지 않고 DataTable에서 가져오도록 했다. 적 캐릭터가 능력치를 읽은 뒤 AI Controller에 넘기면, Controller는 Blackboard에 필요한 값을 저장한다.

```cpp
void AEnemyBaseAIController::InitializeBlackBoard(
    float AttackRadius,
    float AttackSpeed,
    EEnemyTargetPriority TargetPriority)
{
    GetBlackboardComponent()->SetValueAsFloat("AttackRadius", AttackRadius);
    GetBlackboardComponent()->SetValueAsFloat("AttackSpeed", AttackSpeed);
    GetBlackboardComponent()->SetValueAsEnum(
        "TargetPriority",
        static_cast<uint8>(TargetPriority)
    );
}
```

이 구조를 사용하면 Behavior Tree Task가 적 캐릭터의 내부 구현을 계속 들여다보지 않아도 된다. 공격 Task는 Blackboard의 `AttackRadius`, `AttackSpeed`, `TargetPriority`, `AttackTarget`, `State` 같은 키를 기준으로 판단하고, 세부 수치는 DataTable에서 관리된다.

블루프린트와 DataTable을 많이 쓰는 UE 프로젝트에서는 이 분리가 특히 중요했다. 기획자가 스테이지별 적 데이터를 바꾸더라도 C++ Task 흐름은 유지되고, 새로운 적 타입을 추가할 때도 필요한 값만 Row로 추가하면 되기 때문이다.

## 5. 공격 몽타주와 Animation Notify State

공격은 AI Controller가 직접 데미지를 주는 방식으로 만들지 않았다. Behavior Tree가 "공격해야 한다"고 판단하면 적 캐릭터의 `Attack` 함수를 호출하고, 실제 피격 판정은 공격 애니메이션의 특정 구간에서만 열리도록 했다.

```cpp
void ASOWCharacterEnemyBase::Attack(const ASOWCharacter* TargetActor)
{
    if (AttackAnimation)
    {
        UAnimInstance* const EnemyAnimInstance = GetMesh()->GetAnimInstance();
        EnemyAnimInstance->Montage_Play(AttackAnimation);
    }
}
```

이후 `UANS_MeleeAttack`에서 근접 공격 판정을 처리했다. Animation Notify State가 시작되면 공격하는 적을 캐싱하고, Tick 동안 전방 구체 Sweep으로 피격 대상을 찾는다.

```cpp
const FVector Start =
    GetEnemyChar()->GetActorLocation()
    + GetEnemyChar()->GetActorForwardVector()
    * GetEnemyChar()->GetCapsuleComponent()->GetScaledCapsuleRadius();

const FVector End =
    Start + GetEnemyChar()->GetActorForwardVector() * AttackRange;

bool bHit = MeshComp->GetWorld()->SweepSingleByChannel(
    Hit,
    Start,
    End,
    FQuat::Identity,
    ECollisionChannel::ECC_Pawn,
    FCollisionShape::MakeSphere(AttackRadius),
    CollisionQueryParams
);
```

공격 판정을 애니메이션에 붙인 이유는 명확했다. 적의 손, 무기, 몸통이 실제로 공격하는 프레임과 데미지 타이밍이 맞아야 플레이어 입장에서 납득할 수 있기 때문이다. 특히 SOW는 많은 적이 한꺼번에 등장하는 운빨 가차 랜덤 디펜스이므로, 공격 타이밍이 어긋나면 난이도가 불공정하게 느껴질 수 있었다.

## 6. GAS GameplayEffect 적용

피격 대상이 확인되면 바로 체력을 깎지 않고, 대상이 SOW 캐릭터 타입 인터페이스를 구현하는지 확인한 뒤 GameplayEffectSpec을 만들어 Target ASC에 적용했다.

```cpp
if (TargetType == ESOWCharacterType::Player || TargetType == ESOWCharacterType::Turret)
{
    USOWBlueprintFunctionLibrary::NativeGetSOWAbilitySystemComponentFromActorInfo(Enemy)
        ->ApplyGameplayEffectSpecToTarget(
            *USOWBlueprintFunctionLibrary::NativeGetSOWAbilitySystemComponentFromActorInfo(Enemy)
                ->MakeOutgoingSpec(DamageEffect, 1.f, EffectContext).Data.Get(),
            USOWBlueprintFunctionLibrary::NativeGetSOWAbilitySystemComponentFromActorInfo(Hit.GetActor())
        );

    bCanInflictDamage = false;
}
```

여기서 `bCanInflictDamage`를 둔 이유는 Notify State가 여러 프레임 동안 Tick되기 때문이다. 공격 구간 안에서 Sweep이 여러 번 성공해도 한 번의 공격 몽타주가 여러 번 데미지를 넣으면 안 된다. 따라서 한 번 데미지를 적용한 뒤에는 Notify가 끝날 때까지 추가 데미지를 막았다.

GAS를 사용하면서 얻은 장점은 데미지 적용이 캐릭터별 구현에서 분리된다는 점이었다. 적이 플레이어를 때리든, 터렛을 때리든, Core Rune을 때리든, 결국 ASC와 GameplayEffect를 통해 동일한 규칙으로 처리할 수 있다.

## 7. 적 능력치 초기화

적의 MaxHealth, AttackSpeed, AttackPowerBase 같은 값은 `GEEC_InitEnemyAttributes`에서 DataTable Row를 읽어 GAS Attribute로 덮어쓴다.

```cpp
if (ASOWCharacterEnemyBase* Enemy = Cast<ASOWCharacterEnemyBase>(
    ExecutionParams.GetSourceAbilitySystemComponent()->GetAvatarActor()))
{
    const auto EnemyAttributesData =
        Enemy->EnemyAttributesDT.DataTable->FindRow<FEnemyAttributeData>(
            Enemy->GetEnemyTypeStr(),
            ""
        );

    if (!EnemyAttributesData) return;

    OutExecutionOutput.AddOutputModifier(
        FGameplayModifierEvaluatedData(
            GetCapturedEnemyAttributes().MaxHealthBaseDef.AttributeToCapture,
            EGameplayModOp::Override,
            EnemyAttributesData->MaxHealth
        )
    );
}
```

이 작업은 적 AI와 GAS를 연결하는 또 다른 지점이었다. AI는 공격 속도와 공격 범위 같은 판단 값을 필요로 하고, GAS는 체력과 공격력 같은 전투 값을 필요로 한다. 둘 다 같은 DataTable을 출발점으로 삼으면 적 타입을 추가하거나 밸런스를 바꿀 때 기준이 흩어지지 않는다.

## 8. 후기

이 시기의 작업은 SOW에서 내가 맡은 적 시스템의 기반을 잡는 단계였다. 눈에 보이는 결과물은 "적이 걷고 공격하고 죽는다" 정도로 단순해 보일 수 있지만, 내부적으로는 Behavior Tree, Blackboard, Animation Notify State, DataTable, GAS가 서로 맞물려 있었다.

특히 공격을 애니메이션 타이밍에 맞추고, 실제 데미지는 GAS Effect로 처리한 구조가 이후 작업에 큰 도움이 되었다. 이후 적 경로 이동, Core Rune 충돌, 웨이브 버프, 저항 태그, 샤드 드롭 같은 기능을 추가할 때도 이 흐름 위에 얹을 수 있었기 때문이다.
